# DECISIONS

영구적인 설계 결정과 그 이유. 번호를 이어서 쌓고 지우지 않는다. 뒤집힌 결정은 "D-NNN으로 대체"라고 표시한다.

## D-001 실행 방식: GitHub Actions 예약 실행 (2026-11-02, 제안)

- 맥락: PC와 WSL이 꺼져 있어도 알림이 와야 한다. 서버 비용은 0원이 좋다.
- 결정: 파이썬 스크립트를 GitHub Actions `schedule`(cron, 15분 간격)로 돌리고, 이미 알린 글 목록(`state/seen.json`)을 실행 끝에 저장소에 커밋한다.
- 대안:
  - Windows 작업 스케줄러: PC가 켜져 있을 때만 동작한다.
  - 웨일 확장(`chrome.alarms` + `chrome.notifications`): 이미 익숙하지만 브라우저가 켜져 있을 때만 동작하고 휴대폰 알림이 없다. M4 이후 "PC 알림창" 보조로 다시 볼 수 있다.
  - 오라클 무료 VM, 라즈베리파이: 상시 실행은 되지만 관리할 것이 늘어난다.
  - changedetection.io(셀프 호스팅): 코딩 없이 페이지 변화 감시는 되지만, 분류와 키워드 기준 매칭이 약하고 서버가 필요하다.
- 주의:
  - Actions cron은 정시에 돌지 않고 수 분에서 수십 분 늦을 수 있다. 공개 저장소는 60일 동안 커밋이 없으면 예약 실행이 꺼진다(state 커밋이 이를 막아 준다).
  - 비공개 저장소는 월 무료 시간이 정해져 있다. 15분마다 1분이면 한 달 약 2,900분이라 넘칠 수 있다. 비공개라면 30분 간격이나 공개 저장소(비밀은 Secrets)를 검토한다. 정확한 한도는 구현 시점에 GitHub 문서로 다시 확인한다.
  - 러너는 해외 IP다. 학교 서버가 해외 접속을 막으면 이 결정을 다시 한다(M1 계획 1단계).
  - 실행이 겹치면 같은 state로 둘 다 알림을 보낸다. 워크플로에 `concurrency: { group: notice, cancel-in-progress: false }`를 둬 한 번에 하나만 돌게 한다.
    state 커밋은 push 실패 시 `git pull --rebase` 후 최대 3회 재시도한다. 사람은 state를 고치지 않으므로 충돌은 봇 커밋끼리만 생긴다.

## D-002 알림 채널: Apprise로 보내고 기본 수신은 ntfy (2026-11-02, 제안)

- 결정: 보내기는 Apprise 라이브러리 하나로 한다. URL만 바꾸면 ntfy, 텔레그램, 디스코드, 이메일, 윈도우 토스트로 갈아탈 수 있다.
  기본 수신은 ntfy 앱(안드로이드, iOS, 웹/PC)이다. 계정이 필요 없고, 알림에 클릭 URL을 붙이면 누를 때 원문이 열린다.
- 대안: 텔레그램 봇(봇 토큰 발급 필요, 채팅 기록이 남아 좋음), 카카오톡(공식 API 제약이 큼), 직접 만든 앱(범위 밖).
- 주의: ntfy 공개 서버(ntfy.sh)의 토픽은 이름을 아는 누구나 구독할 수 있다. 추측 불가능한 이름을 쓰고 비밀로 다룬다. 민감하면 셀프 호스팅이나 텔레그램으로 바꾼다.

## D-003 HTML 파싱: httpx + selectolax, 셀렉터는 설정 파일에 (2026-11-02, 제안)

- 맥락: 두 게시판 모두 학교 CMS의 같은 마크업(`ul.board-list-wrap > li`, `?mode=view&articleNo=`)을 쓴다. 자바스크립트 렌더링이 필요 없다.
- 결정: Selenium 없이 httpx로 받고 selectolax(또는 BeautifulSoup)로 읽는다. 게시판마다 다른 부분(기본 URL, 파서 종류)은 `config/sources.yaml`에 둔다.
- 근거: 기존 성대 봇들은 Selenium과 ChromeDriver를 써서 무겁고 Actions에서 느리다.

## D-004 글의 고유 키는 (게시판 id, articleNo) (2026-11-02)

- 제목은 수정될 수 있고 상단 고정 글은 매번 다시 나온다. URL의 `articleNo`는 게시판 안에서 변하지 않는다.
- state에는 키와 처음 본 시각, 알림 여부만 저장한다. 오래된 키는 개수 상한(게시판당 최근 500개)으로 잘라 파일이 커지지 않게 한다.

## D-005 실패 처리 순서 (2026-11-02, 제안)

- 한 실행에서: 받기, 파싱, 새 글 판정, 매칭, 알림, state 저장 순서다.
- 전달 보장은 "적어도 한 번"이다. 알림 성공 뒤 state 저장이나 커밋이 실패하면 다음 실행에서 같은 글이 한 번 더 갈 수 있다. 누락보다 낫다고 보고 감수한다.
- 알림이 실패한 글은 state에 `pending`과 `attempts`(실패 횟수)로 저장하고 다음 실행에서 다시 보낸다. **3번째 실패 직후** `failed`로 바꾸고 더는 보내지 않는다.
- 파싱 결과가 0건이면 "게시판 구조가 바뀜"으로 보고 그 게시판 state를 건드리지 않으며, 실패 알림(선택)을 보낸다.
- 첫 실행(그 게시판 state 없음)은 알림 없이 현재 글을 모두 `baseline`으로 저장만 한다.
- 규칙은 **새 글에만** 적용한다. 규칙을 바꿔도 이미 `skipped`인 글을 다시 평가하지 않는다. 지난 글을 새 기준으로 보고 싶으면 `--dry-run --all`로 미리 보기만 한다.
- 1페이지 일반 글이 모두 새 글이면(겹치는 글 없음) 실행 사이에 더 많이 올라온 것이므로 다음 페이지를 최대 2페이지 더 읽는다(`crawling.md`).

## D-006 남의 코드는 라이선스 따지지 않고 가져다 쓴다 (2026-11-02, 확정)

- 사용자 지시: "코드를 그냥 막 활용해도 돼", "라이선스 신경쓰지말고 그냥 막 활용해."
- 결정: 직접 짜기 전에 `docs/research/open-source.md`의 저장소에서 가져올 코드를 먼저 찾는다. 라이선스 확인 절차는 두지 않는다.
- 가져온 파일 머리에 `# 출처: <URL>` 한 줄만 남긴다. 원본이 고쳐졌을 때 비교하고, 버그를 추적하려는 용도다.
- 참고: 저장소를 공개로 바꾸게 되면 그때 한 번 출처 주석을 훑어본다(이 결정을 다시 볼 유일한 시점).

## D-007 API: 1단계 정적 JSON(GitHub Pages), 2단계 FastAPI (2026-11-02, 제안)

- 사용자 지시: "api 이런거도 만들어서 활용하자."
- 맥락: 알림만으로는 지난 공지 검색, 다른 화면(웨일 확장 팝업, 위젯, 단축어)에서 보기가 어렵다. PC가 꺼져 있어도 API가 살아 있어야 한다.
- 결정:
  - 1단계(M3에 붙임): Actions가 실행마다 `site/api/v1/`에 JSON을 만들어 GitHub Pages로 낸다. 서버 비용 0원, 항상 켜져 있음.
    `notices.json`(전체 최근 글), `boards/<id>.json`, `matched.json`(내 기준에 맞은 글), `deadlines.ics`(마감 캘린더), `feed.xml`(RSS).
  - 2단계(M5): 검색, 필터, 구독 설정 수정이 필요해지면 [tsungmnli/skku-notice-api](https://github.com/tsungmnli/skku-notice-api)의 FastAPI 구조를 가져와 띄운다. 호스팅(무료 PaaS, 오라클 VM, 로컬 Windows)은 그때 정한다.
- 주의: Pages는 저장소가 공개이거나 유료 요금제여야 한다. 공개하면 `matched.json`, `config/rules.yaml`, `state/seen.json`의 상태값이 내 관심사를 드러낸다.
  **M3 시작 전에 사용자가 정한다**: (가) 비공개 저장소, Pages 없음, API는 2단계에서 / (나) 공개 저장소, `notices.json`과 `boards/`만 공개하고 개인 파일은 내보내지 않으며 state는 키만 저장 / (다) 데이터만 따로 공개 저장소로 push.
- 대안: 처음부터 FastAPI 서버 상시 실행. 관리할 서버가 생기고 PC가 꺼지면 같이 꺼지므로 2단계로 미뤘다.
