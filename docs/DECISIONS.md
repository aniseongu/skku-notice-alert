## D-001 실행 방식: GitHub Actions 예약 실행 (2026-11-02, 제안)

- 맥락: PC와 WSL이 꺼져 있어도 알림이 와야 한다. 서버 비용은 0원이 좋다.
- 결정: 파이썬 스크립트를 GitHub Actions `schedule`(cron, 15분 간격)로 돌리고, 이미 알린 글 목록(`state/seen.json`)을 실행 끝에 저장소에 커밋한다.
- 대안:
  - Windows 작업 스케줄러: PC가 켜져 있을 때만 동작한다.
  - 웨일 확장(`chrome.alarms` + `chrome.notifications`): 이미 익숙하지만 브라우저가 켜져 있을 때만 동작하고 휴대폰 알림이 없다. M4 이후 "PC 알림창" 보조로 다시 볼 수 있다.
  - 오라클 무료 VM, 라즈베리파이: 상시 실행은 되지만 관리할 것이 늘어난다.
  - changedetection.io(셀프 호스팅): 코딩 없이 페이지 변화 감시는 되지만, 분류와 키워드 기준 매칭이 약하고 서버가 필요하다.
- 주의:
  - Actions cron은 정시에 돌지 않고 수 분에서 수십 분 늦을 수 있다. 공개 저장소는 60일 동안 커밋이 없으면 예약 실행이 꺼진다(state 커밋이 이를 막아 준다).
  - 비공개 저장소는 월 무료 시간이 정해져 있다. 15분마다 1분이면 한 달 약 2,900분이라 넘칠 수 있다. 비공개라면 30분 간격이나 공개 저장소(비밀은 Secrets)를 검토한다. 정확한 한도는 구현 시점에 GitHub 문서로 다시 확인한다.
  - 러너는 해외 IP다. 학교 서버가 해외 접속을 막으면 이 결정을 다시 한다(M1 계획 1단계).
  - 실행이 겹치면 같은 state로 둘 다 알림을 보낸다. 워크플로에 `concurrency: { group: notice, cancel-in-progress: false }`를 둬 한 번에 하나만 돌게 한다.
    state 커밋은 push 실패 시 `git pull --rebase` 후 최대 3회 재시도한다. 사람은 state를 고치지 않으므로 충돌은 봇 커밋끼리만 생긴다.

## D-002 알림 채널: Apprise로 보내고 기본 수신은 ntfy (2026-11-02, 제안)

- 결정: 보내기는 Apprise 라이브러리 하나로 한다. URL만 바꾸면 ntfy, 텔레그램, 디스코드, 이메일, 윈도우 토스트로 갈아탈 수 있다.
  기본 수신은 ntfy 앱(안드로이드, iOS, 웹/PC)이다. 계정이 필요 없고, 알림에 클릭 URL을 붙이면 누를 때 원문이 열린다.
- 대안: 텔레그램 봇(봇 토큰 발급 필요, 채팅 기록이 남아 좋음), 카카오톡(공식 API 제약이 큼), 직접 만든 앱(범위 밖).
- 주의: ntfy 공개 서버(ntfy.sh)의 토픽은 이름을 아는 누구나 구독할 수 있다. 추측 불가능한 이름을 쓰고 비밀로 다룬다. 민감하면 셀프 호스팅이나 텔레그램으로 바꾼다.

## D-003 HTML 파싱: httpx + selectolax, 셀렉터는 설정 파일에 (2026-11-02, 제안)

- 맥락: 두 게시판 모두 학교 CMS의 같은 마크업(`ul.board-list-wrap > li`, `?mode=view&articleNo=`)을 쓴다. 자바스크립트 렌더링이 필요 없다.

- 근거: 기존 성대 봇들은 Selenium과 ChromeDriver를 써서 무겁고 Actions에서 느리다.

## D-004 글의 고유 키는 (게시판 id, articleNo) (2026-11-02)

- 제목은 수정될 수 있고 상단 고정 글은 매번 다시 나온다. URL의 `articleNo`는 게시판 안에서 변하지 않는다.
- state에는 키와 처음 본 시각, 알림 여부만 저장한다. 오래된 키는 개수 상한(게시판당 최근 500개)으로 잘라 파일이 커지지 않게 한다.

## D-005 실패 처리 순서 (2026-11-02, 제안)

- 한 실행에서: 받기, 파싱, 새 글 판정, 매칭, 알림, state 저장 순서다.
- 전달 보장은 "적어도 한 번"이다. 알림 성공 뒤 state 저장이나 커밋이 실패하면 다음 실행에서 같은 글이 한 번 더 갈 수 있다. 누락보다 낫다고 보고 감수한다.
- 알림이 실패한 글은 state에 `pending`과 `attempts`(실패 횟수)로 저장하고 다음 실행에서 다시 보낸다. **3번째 실패 직후** `failed`로 바꾸고 더는 보내지 않는다.
- 파싱 결과가 0건이면 "게시판 구조가 바뀜"으로 보고 그 게시판 state를 건드리지 않으며, 실패 알림(선택)을 보낸다.
- 첫 실행(그 게시판 state 없음)은 알림 없이 현재 글을 모두 `baseline`으로 저장만 한다.
- 규칙은 **새 글에만** 적용한다. 규칙을 바꿔도 이미 `skipped`인 글을 다시 평가하지 않는다. 지난 글을 새 기준으로 보고 싶으면 `--dry-run --all`로 미리 보기만 한다.
- 1페이지 일반 글이 모두 새 글이면(겹치는 글 없음) 실행 사이에 더 많이 올라온 것이므로 다음 페이지를 최대 2페이지 더 읽는다(`crawling.md`).

## D-006 남의 코드는 라이선스 따지지 않고 가져다 쓴다 (2026-11-02, 확정)

- 사용자 지시: "코드를 그냥 막 활용해도 돼", "라이선스 신경쓰지말고 그냥 막 활용해."
- 결정: 직접 짜기 전에 `docs/research/open-source.md`의 저장소에서 가져올 코드를 먼저 찾는다. 라이선스 확인 절차는 두지 않는다.
- 가져온 파일 머리에 `# 출처: <URL>` 한 줄만 남긴다. 원본이 고쳐졌을 때 비교하고, 버그를 추적하려는 용도다.
- 참고: 저장소를 공개로 바꾸게 되면 그때 한 번 출처 주석을 훑어본다(이 결정을 다시 볼 유일한 시점).

## D-007 API: 1단계 정적 JSON(GitHub Pages), 2단계 FastAPI (2026-11-02, 제안)

- 사용자 지시: "api 이런거도 만들어서 활용하자."
- 맥락: 알림만으로는 지난 공지 검색, 다른 화면(웨일 확장 팝업, 위젯, 단축어)에서 보기가 어렵다. PC가 꺼져 있어도 API가 살아 있어야 한다.
- 결정:
  - 1단계(M3에 붙임): Actions가 실행마다 `site/api/v1/`에 JSON을 만들어 GitHub Pages로 낸다. 서버 비용 0원, 항상 켜져 있음.
    `notices.json`(전체 최근 글), `boards/<id>.json`, `matched.json`(내 기준에 맞은 글), `deadlines.ics`(마감 캘린더), `feed.xml`(RSS).
  - 2단계(M5): 검색, 필터, 구독 설정 수정이 필요해지면 [tsungmnli/skku-notice-api](https://github.com/tsungmnli/skku-notice-api)의 FastAPI 구조를 가져와 띄운다. 호스팅(무료 PaaS, 오라클 VM, 로컬 Windows)은 그때 정한다.
- 주의: Pages는 저장소가 공개이거나 유료 요금제여야 한다. 공개하면 `matched.json`, `config/rules.yaml`, `state/seen.json`의 상태값이 내 관심사를 드러낸다.
  **M3 시작 전에 사용자가 정한다**: (가) 비공개 저장소, Pages 없음, API는 2단계에서 / (나) 공개 저장소, `notices.json`과 `boards/`만 공개하고 개인 파일은 내보내지 않으며 state는 키만 저장 / (다) 데이터만 따로 공개 저장소로 push.
- 대안: 처음부터 FastAPI 서버 상시 실행. 관리할 서버가 생기고 PC가 꺼지면 같이 꺼지므로 2단계로 미뤘다.

## D-008 "나에게 해당" 판정: 규칙 다음에 Gemini (2026-11-02, 확정)

- 사용자 지시: "나한테 해당되는건지 아닌지 판단 가능한 것", "gemini api key 활용(무료)". 프로필 범위는 "자세한 프로필"을 선택.
- 결정: 공통 제외어에 걸리지 않은 새 글을 한 실행에 한 번 묶어 Gemini(무료 등급 Flash-Lite 계열)에 보내 relevant, maybe, not_relevant와 이유 한 줄을 받는다.
  규칙에 맞은 글은 AI가 not_relevant라도 low로 알린다(누락보다 중복). AI 실패나 키 없음이면 규칙 결과만 쓴다.
- 비밀: `GEMINI_API_KEY`는 `.env`와 Secrets에만. 프로필은 `config/profile.yaml`(gitignore), Actions에서는 Secret `PROFILE_YAML`.
- 주의: 무료 등급은 입력이 Google 제품 개선에 쓰일 수 있다(2026-11-02 pricing 페이지 확인). 프로필에 이름, 학번, 연락처는 넣지 않는다.
  무료 한도 수치는 문서마다 다르고 자주 바뀐다. 하루 수십 건이라 넉넉하다고 보지만, 429가 잦으면 모델이나 `max_per_run`을 바꾼다.

## D-009 화면: PWA + Beer CSS, 푸시는 ntfy (2026-11-02, 확정, 스타일 부분은 D-011로 대체)

- 사용자 지시: "안드로이드 기반", 디자인 자료(awesome-android-ui, penpot, ui-design 토픽 등) 활용, "너가 복합적으로 생각해서 추천하는 거로".
- 결정: 빌드 없는 PWA(HTML, CSS, JS)를 정적 API와 같이 Pages에 올리고 안드로이드 크롬에서 홈 화면에 설치한다. 스타일은 Beer CSS(Material 3, CDN).
  알림은 계속 ntfy 앱이 맡는다(D-002).
- 근거: 네이티브 앱도 서버나 FCM 없이는 푸시를 못 받는다. 그러면 앱은 목록을 보는 화면일 뿐이라 PWA로 충분하다. 만들 양과 유지 비용이 가장 작다.
  awesome-android-ui는 대부분 View(XML) 시대 라이브러리라 지금 쓸 것이 적고, Penpot은 화면 하나짜리 개인 도구에는 과하다.
  @material/web은 유지 모드 공지가 있고 Pico CSS는 보관(archived) 상태라 뺐다(2026-11-02 확인).
- 대안: Kotlin + Jetpack Compose 앱(android/nowinandroid 구조). 위젯이나 오프라인 동기화가 꼭 필요해지면 다시 본다.

## D-011 화면 구성: pwa-starter 방식(Vite, Lit, Workbox), 직접 만든 디자인 체계 (2026-11-02, 확정)

- 유리 효과는 탐색(상단 바, 하단 탭)에만 쓴다. 웨일 DESIGN의 "장식용 글래스모피즘 금지"와 사용자의 토스 글래스 선호를 함께 만족시키는 선이다.
- 앱 아이콘은 아캠 플러스 아이콘(CC BY-SA 4.0 사진에서 딴 선)을 바탕으로 한다. 공개 배포할 때 출처를 README에 둔다.
- 빌드: `cd web && npm run build`. Actions(M3)에는 Node 설정과 이 단계가 export 앞에 들어가야 한다.

## D-012 Canvas(아이캠퍼스) 강의, 과제 알림은 개인 토큰으로, 알림만 (2026-11-02, 확정)

- 결정: Actions 실행에서 `CANVAS_TOKEN`(사용자가 아이캠퍼스에서 만든 액세스 토큰)으로 Canvas API를 읽어 하루 요약과 마감 리마인드를 ntfy로 보낸다.
  과제 목록은 `site/`로 내보내지 않고, state에는 항목 키와 보낸 단계만 둔다. 계획: `docs/plans/2026-11-02_canvas-alerts.md`.
- 근거: 웨일 아캠 플러스는 PC 브라우저가 켜져 있을 때만 알린다. learningx-alert.com도 같은 토큰 방식이다.
- 주의: 토큰은 계정 전체 권한이다. 새면 아이캠퍼스에서 폐기한다. 해외 IP 접속 가능 여부는 M3에서 확인.

## D-013 새 글 본문을 읽어 앱에서 보여 주고 Gemini가 요약한다 (2026-11-02, 확정)

- 사용자 질문: "내용을 꼭 사이트 들어가서 확인해야하는건가?"
- 결정: 새 글의 상세 페이지를 한 번만 읽어 본문 글자와 첨부 목록을 저장하고, 판정과 같은 Gemini 호출에서 해요체 세 줄 요약을 받는다.
  `site/api/v1/notices/<게시판>/<글번호>.json`(요약, 본문, 첨부)으로 따로 내보내 목록 JSON을 가볍게 둔다(D-010에 추가하는 파일, 기존 필드는 그대로).
  앱은 휴대폰에서도 행을 누르면 앱 안 상세 화면을 먼저 보여 주고, 원문은 "원문 열기"로 연다.
- 요청 수: 새 글에만, 실행당 게시판별 최대 5건, 게시판 사이 1초(crawling.md). 하루 새 글이 수십 건 이하라 학교 서버 부담은 목록 요청과 비슷한 수준이다.
- 판정도 좋아진다: 제목에 없는 지원 자격(학년, 학과 제한)이 본문에 있는 경우가 많다.
- 주의: 표는 글자만 남긴다. 본문 그림은 주소만 저장하고(최대 10개, 사이트 꾸밈 그림 제외) 앱이 볼 때 학교 서버에서 받는다. 학과 공지는 본문이 그림뿐인 글이 많다(2026-11-02 fixture로 확인). 첨부는 이름과 링크만 두고 내려받지 않는다.

## D-014 그림으로만 올라온 본문은 Gemini가 읽어 글로 옮긴다 (2026-11-02, 확정)

- 사용자 질문: "본문 글자들은 왜 안 받아?" 학과 공지는 본문이 포스터 그림 하나뿐이고 HTML에 글자와 그림 설명이 없다(fixture로 확인).
- 결정: 본문 글자가 거의 없는 새 글은 본문 그림을 받아 판정 호출에 함께 넣고, Gemini가 그림 속 글자를 옮겨 적고(body_text), 요약과 판정도 그림 내용을 보고 한다.
  글별 JSON에 `body_from_image: true`를 더한다(추가 필드). 앱은 "그림에서 읽은 글이라 틀릴 수 있어요"를 같이 보여 주고 그림도 그대로 둔다.
- 대안: Tesseract, PaddleOCR(키 불필요). 디자인된 한국어 포스터 정확도가 낮고 Actions에 한국어 모델 설치가 필요해 뺐다.
- 요청 수: 그림은 글당 3개, 실행당 10개까지(crawling.md). Gemini 키가 없으면 그림을 받지 않는다.

## D-015 그림 글자는 오픈소스 OCR(RapidOCR)로 먼저 읽고, 새 공지는 모두 알린다 (2026-11-02, 확정)

- 사용자 지시: "글자가 적혀있는거라면 학과공지도 읽어서 받을 수 있는 오픈소스 모델이나 이런거 있으면 적용하라고", "공지 모두 알림은 왔으면 좋겠는데?"
- OCR: RapidOCR(RapidAI/RapidOCR, Apache-2.0, 3.10.0)로 PP-OCRv5 한국어 인식 모델을 onnxruntime CPU에서 돌린다. 키 없이 그림 속 글자를 body_text로 저장하고,
  Gemini 키가 있으면 OCR 글자와 그림을 함께 보고 요약과 판정을 한다(D-014를 보완). PaddleOCR(무거움), EasyOCR(갱신 멈춤), Tesseract(포스터에 약함)는 뺐다.
  모델 파일은 처음 실행에서 받아 Actions 캐시에 둔다. 그림 요청 상한은 D-014 그대로.
- 알림: 새 공지는 모두 ntfy로 보낸다. 기준, 관심 키워드, Gemini 해당은 소리 있게(priority 원래대로), 나머지는 조용히(low, 소리와 진동 없음).
  "내 공지" 탭은 기준, 관심 키워드, Gemini 해당과 확인 필요만 모은다(알림을 보냈다는 이유로 넣지 않는다).
- 예시 규칙 "학과 공지는 모두 (조용히)"는 이 설정으로 대체해 지운다.
