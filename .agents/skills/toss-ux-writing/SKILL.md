# 토스식 UX 라이팅 + 설정 UI

문구와 흐름은 이 스킬을, 모양은 `docs/DESIGN.md` §1 금지 목록과 `extensions/<slug>/DESIGN.md`를 따른다.
**둘이 부딪히면 이렇게 정한다.**

- `icampus-check`: 시각은 원본 iCampusCheck 디자인이 이긴다(원본 변수, `table`/`.btn`/`.playlist-action` 부품, Pretendard, 폭 600px).
  토스의 세그먼트, 스위치 같은 **모양은 가져오지 않는다.** 토스 방식은 **문구와 흐름**에만 적용한다.
- `docs/DESIGN.md` §1 금지(왼쪽 굵은 선, 이모지 아이콘 추가, "→", "A · B · C", 애니메이션 등)는 항상 이긴다.
- 확장 이름은 "아캠 매니저"(icampus-check)처럼 사용자에게 보이는 이름을 쓴다. 코드명을 문구에 쓰지 않는다.

## 1. 말투 (토스 UX 라이팅 가이드)

| 규칙 | 이렇게 | 이렇게 쓰지 않는다 |
| --- | --- | --- |
| 해요체로 통일한다 | "바로 적용돼요" | "적용됨", "적용됩니다" |
| 능동형이 기본이다. 상태 설명에만 수동 | "저장했어요" | "저장됐어요" |
| `돼요`를 쓴다 | "다시 열면 돼요" | "되어요" |
| 긍정형으로 쓴다. 안 되는 일은 하면 되는 일로 | "로그인하면 볼 수 있어요" | "로그인하지 않으면 볼 수 없어요" |
| 과한 높임을 쓰지 않는다 | "바꿀까요?" | "바꾸시겠어요?" |
| 명사를 쌓지 않는다 | "과제 알림을 받아요" | "과제 알림 수신 설정 안내" |
| 사용자 언어로 쓴다 | "화면 모드", "알림" | "테마", "웹훅 설정" |
| 군더더기를 지운다(잡초 뽑기) | "자동은 브라우저 설정을 따라요" | "앞으로 자동을 선택하시면 브라우저의 설정에 맞추어…" |
| 한 문장에 하나만 말한다. 소리 내어 읽어 자연스러운지 본다 | | 한 문장에 두 가지 안내 |

- 부정형은 정책이나 기술 한계로 정말 안 될 때만 쓰고, **이유를 같이** 쓴다("이 페이지는 아직 지원하지 않아요").
- 접속, 조회 실패 같은 오류는 사과하지 않고 **무엇을 하면 되는지** 쓴다: "아이캠퍼스에 로그인한 뒤 다시 열어 주세요."
- 한자어 명사 대신 동사로 푼다("완료" -> "끝났어요").
- 강요하거나 겁주지 않는다. 선택지는 중립으로 쓴다(토스 "제안하되 강요하지 않기").

## 2. 버튼

- 버튼은 **누르면 일어날 일**을 동사로 쓴다: "저장하기", "다시 불러오기". 결과 알림은 같은 동사로 받는다("저장했어요").
- 한 버튼이면 `~하기`. 다음 화면으로 가면 "확인"이나 "다음".
- 닫는 버튼은 "취소"가 아니라 **"닫기"**(작업이 취소된다고 오해한다). 대화상자 둘 중 하나는 "다음에" 정도로 부드럽게.
- 버튼 위에 장점을 반복하는 문구나 부풀린 안내를 얹지 않는다. 끝에 "→" 금지(DESIGN §1).

## 3. 설정 화면 (화면 모드를 예로)

**구조**: 왼쪽 라벨, 오른쪽 컨트롤인 한 줄. 카드로 감싸지 않는다(DESIGN §2). 한 줄에 결정 하나.

```
화면 모드            [ 자동 | 밝게 | 어둡게 ]
자동은 브라우저 설정을 따라요
```

- **라벨**은 명사 두세 글자의 사용자 말: "화면 모드". "테마", "Appearance", "다크 모드 설정"이 아니다.
- **선택지**는 짧은 부사형 하나씩: "자동", "밝게", "어둡게". 서로 겹치지 않고, 같은 품사로 맞춘다.
  "라이트/다크"는 영어 외래어라 쓰지 않는다.
- **도움말**은 라벨 아래에 해요체 한 줄만. 모든 선택지를 설명하지 않고 **헷갈리는 하나만**("자동은 브라우저 설정을 따라요").
  이미 보이는 것은 쓰지 않는다("밝게를 선택하면 밝아져요" 금지).
- **즉시 반영**한다. 고르면 바로 화면이 바뀌고 저장 버튼, 확인 대화상자, 토스트가 없다. 바뀐 화면이 곧 피드백이다.
  저장 결과를 알려야 하면(보이지 않는 설정) "저장했어요" 한 줄을 인라인으로.
- **기본값이 있다.** 처음 열 때 이미 "자동"이 골라져 있고, 아무것도 안 골라도 쓸 수 있다. 열자마자 선택을 강요하는 안내나 모달을 띄우지 않는다.
- 선택지가 셋 이상이고 하나만 고르면 한 줄에 나란히(또는 라디오). 켜고 끄기 둘이면 스위치. (일반 설정 UX 관행)
  이 확장에서는 새 부품을 만들지 말고 원본 부품(`.playlist-action` 계열을 묶은 버튼 줄, 선택된 것은 주 버튼 배경 `--table-header`)으로 만든다.
- 선택된 상태는 **색만으로** 구분하지 않는다(배경 + 굵기, `aria-pressed`/`aria-checked`). 포커스 윤곽선을 남긴다.
- 상태는 정확하게 보여 준다. 오류가 아닌데 경고 아이콘을 쓰지 않고, 기다릴 게 없는데 로딩 표시를 쓰지 않는다.
- 설정 화면에 환영 문구, 통계 타일, 설명 단락을 넣지 않는다. 한 화면의 중심은 하나다.

## 4. 문구 점검표 (쓰고 나서 훑는다)

1. 해요체인가. "~합니다", "~됨"이 섞이지 않았는가.
2. 능동형인가("했어요"). 안 되는 일은 하면 되는 일로 바꿨는가.
3. 지워도 뜻이 같은 단어(앞으로, 매우, 다음과 같이)가 있는가.
4. 버튼이 동사이고 "취소"가 아니라 "닫기"인가.
5. 오류 문구에 할 일이 있고 사과가 없는가.
6. 코드명, 영어 약어, 개발자 용어가 사용자에게 보이는가.
7. DESIGN §1 문구 금지(eyebrow, ALL-CAPS, "A · B · C", "WORD — 조각", 번호, "→")를 어기지 않았는가.

## 5. 한계

토스 가이드의 예시 문구 대부분은 이미지로만 공개되어 있어 위 표의 예시는 공식 원문 예시와 이 저장소용 예시가 섞여 있다.
"세그먼트 컨트롤/스위치를 언제 쓰나" 같은 컴포넌트 규칙은 토스 공개 문서에서 확인하지 못했다. 그 부분은 일반 관행이다.
